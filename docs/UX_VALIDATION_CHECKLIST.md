# UX Validation Checklist

Use this checklist for the next product review. It is intentionally task-based:
the reviewer should attempt the task first, then record where they hesitated or
needed explanation.

## Dashboard — operate

- [ ] In the first viewport, identify whether anything needs attention.
- [ ] Identify the three outcome metrics without reading technical copy.
- [ ] Run one Quick Check and explain the result in their own words.
- [ ] Find a recent decision and open the full audit trail.
- [ ] Expand **Operating insights** only when looking for trends or technical detail.
- [ ] A new workspace sees setup guidance without a second dashboard underneath.

## Policies — configure

- [ ] From an empty workspace, choose a template or start from scratch.
- [ ] From a populated workspace, find an active or held policy immediately.
- [ ] Explain what a held policy means and find its release action.
- [ ] Test a policy without mistaking “Test” for policy editing.

## API Identities — configure

- [ ] Find the user’s identities without first reading the example section.
- [ ] Understand the difference between an API identity and an example identity.
- [ ] Create an API identity from the page’s primary action.

## Governance Check — test

- [ ] Describe a spend in plain language and submit it.
- [ ] Find the outcome and the policy reason without opening technical detail.
- [ ] Find advanced fields when the default input is insufficient.
- [ ] From a denied result, identify the next corrective action.

## Audit — operate

- [ ] Find the decision timeline without scrolling past architecture copy.
- [ ] Filter to denied decisions.
- [ ] Search for an identity or action.
- [ ] Clear filters after a no-results state.
- [ ] Open one decision and locate its policy explanation/evidence.
- [ ] Open **Proof & security details** only when verification is needed.

## Integrate — build

- [ ] Understand the prerequisite path: policy → API identity → API key.
- [ ] Generate a key and understand that it is shown only once.
- [ ] Find the first working request without opening platform background.
- [ ] Explain what the system should do for an allow versus deny response.

## Sealed Bids — governance workflow

- [ ] Understand that this is confidential vendor selection, not routine spend.
- [ ] Identify **Create agent round** as the recommended governed path.
- [ ] Understand what **Create manually** means before selecting it.
- [ ] Open a round and understand its status and next action.

## Recording results

For each task, record:

| Field | Notes |
| --- | --- |
| Participant type | New / returning / developer / procurement |
| Time to completion | Start and finish timestamps |
| Wrong turns | Routes, controls, or terms misunderstood |
| Help opened | Tooltip, docs, or external help |
| Stopping point | Where they stopped reading or asked for guidance |
| Confidence | 1–5: how confident were they in the result? |

### Acceptance signals

The experience is ready for the next iteration when participants can complete
each route’s primary task without being taught Cognivern’s architecture first,
and when secondary detail is opened intentionally rather than because the
default hierarchy was unclear.
